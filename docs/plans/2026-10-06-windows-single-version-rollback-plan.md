# Windows 安装版单上一版回退：实施与验收计划

日期：2026-10-06。对象：`qwqwd65-ui/cc-switch`。

本文是实施计划，尚未实现回退功能。代码基线为 `e8ed7e017235cb861f49a30917038847c4de31a2`，对应已发布的 `v3.20.4-fork.3`。继续维护 3.x 稳定线，不合入上游 4.0 预览版。首个候选版本暂定 `v3.20.4-fork.4`，发布前检查远端版本是否已被占用。

## 1. 已确定的交付要求

1. 第一版交付 Windows x64 NSIS 安装版的完整更新、快照、回退、失败恢复流程，验证稳定后再扩大范围。不能只交一个备份入口，等待下一版才实现回退。
2. 回退恢复升级前状态，丢弃快照之后的 CC Switch 数据与受管配置变更，不做反向 SQL 迁移，也不尝试合并新旧数据。
3. 永远只有一个可用的上一版回退点。连续升级 `.1 → .2 → .3 → .4` 后，仅可从 `.4` 回到 `.3`，不能继续回到 `.2`。
4. “上一版”是这台机器升级前实际安装的版本，不是按版本号猜一个。跳过版本从 `.1 → .4`，回退目标就是 `.1`。
5. A 路径是默认的联网获取旧版签名安装包；从旧版经支持该协议的应用内更新到当前版，才记录 B 路径并缓存旧版安装包。依据安装事务来源选择，不依据当前网络状态猜测。
6. 点击回退先验证回退点与目标包，再进行两次确认。第二次将确认、取消按钮的位置对调。取消任一确认都不修改正式数据。
7. 页面不加入流程淡入淡出、滑动或按钮移动动画。进度使用静态阶段文字、数字或立即更新的进度条。
8. 本机不运行 Rust 编译、前端构建、完整类型检查或测试。完整检查、测试及安装包构建全部交给 GitHub Actions。
9. 不修改用户原有的 `video-debug/`，不在真实用户数据库或真实安装目录中试验恢复。

## 2. 已核实的代码与必须修正的设计假设

| 现状                                                                        | 证据                                                                   | 对实现的要求                                                       |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 更新由后端下载后调用 Tauri 安装                                             | `src-tauri/src/commands/settings.rs` 中的 `install_update_and_restart` | 将快照与事务记录接入安装之前；不能只改前端                         |
| 数据库版本为 19                                                             | `src-tauri/src/database/mod.rs`                                        | 功能元数据存独立文件，第一版不为回退功能升级业务 schema            |
| `Database::init()` 先 `create_tables()`，随后做迁移前备份，备份失败只记警告 | 同文件                                                                 | 安装快照必须先于正常初始化；回退所需快照失败必须阻止进入新版本     |
| 普通数据库恢复会建表、迁移到当前版本并补定价                                | `src-tauri/src/database/backup.rs` 的 `restore_from_backup`            | 只能复用 SQLite 一致性备份的底层能力，不能调用普通恢复接口实现降级 |
| 正常退出恢复 Live 配置，但清理错误只写日志                                  | `src-tauri/src/lib.rs` 的 `cleanup_before_exit`                        | 新增可返回错误的事务停机接口，不能把日志当成成功凭据               |
| Tauri updater 2.10.0 支持固定 endpoint 和自定义版本比较                     | 本地依赖 `updater.rs`                                                  | A 路径可查指定旧版本，仍要精确匹配目标版本、平台和 fork            |
| Tauri `download()` 验 minisign；`install()` 本身不重新验签                  | 同上                                                                   | B 路径执行本地包前必须重新验签，不能直接把缓存字节交给安装入口     |
| Windows `install_inner()` 用 `ShellExecuteW` 启动安装器后直接退出           | 同上                                                                   | 完整回退需持有安装子进程、等待退出码并验证结果的执行器             |
| NSIS 有 PREINSTALL/POSTINSTALL 钩子                                         | Tauri 配置定义                                                         | 钩子相对旧卸载、进程检查、文件替换的具体顺序仍需验证               |
| 仓库声明 Tauri CLI 2.11.5，本机 node_modules 实际仍为 2.8.1                 | `package.json` 与本地安装目录                                          | 以 GA 中锁定依赖构建的模板为准；不把本机旧模板当成发布依据         |
| `portable.ini` 仍决定便携提示                                               | `src-tauri/src/commands/misc.rs`                                       | Setup 覆盖旧便携目录时的标记清理必须纳入安装测试                   |

需要撤回的早期假设：

- “先安装新版，再运行新版辅助模式备份”有窗口期。正式设计是在旧文件被卸载/覆盖前，由安装器解出的独立辅助程序捕获旧状态。
- “若数据恢复失败，只把当前数据恢复回去就行”不完整。若旧程序已经安装，恢复新数据还必须恢复与之匹配的新程序及安装记录。
- Windows 多文件、跨卷替换不是一个原子事务。使用逐步日志、可重复执行操作和补偿恢复；只把回退点指针的提交称为原子发布。
- 没有升级前快照时，A 也不能制造历史数据。全新安装不显示可执行的回退按钮；缺损回退点显示具体原因，不能任意选一个旧版安装。

## 3. A/B 路径与首版引导

| 安装情况                                       | 快照来源                   | 回退路径                               | 条件                                          |
| ---------------------------------------------- | -------------------------- | -------------------------------------- | --------------------------------------------- |
| 全新安装                                       | 无旧版本                   | 无版本回退                             | 不生成虚构回退点                              |
| 手动用本 fork 新版 Setup 覆盖旧版              | 安装器在替换前捕获         | A：回退时下载固定旧 Release 的包并验签 | 旧版本身份、目录和原数据必须可识别            |
| 带回退协议的旧版从应用内升级                   | 更新协调器与安装器联合捕获 | B：执行缓存的已验签旧版包              | 安装事务明确标为 `in_app_update`，且缓存成功  |
| 不带协议的旧 `fork.3` 经应用内更新至首个新版本 | 新安装器捕获旧数据         | A：兼容引导                            | 旧客户端不会预缓存自己的 Setup；不伪造 B 状态 |
| B 的本地包丢失或损坏                           | 原快照仍有效               | 提示后按 A 重新下载同一个目标包        | 不变更回退目标，重新完成验签与预检            |
| 重装相同版本                                   | 不创建新回退点             | 保留原有回退点                         | 不把 `X → X` 记成升级                         |
| 检测到手动降级                                 | 不生成反向历史链           | 消费/失效不再匹配的回退点              | 不能把新版本记录成“上一版”供回退              |

旧 `fork.3 → 新 fork.4 → fork.3` 的 A 路径必须在首版发布前实际跑通。后续 `fork.4 → fork.5 → fork.4` 的 B 路径通过 GA 中多个测试版本验证，不需要为了测试公开发布空版本。

首版自动回退支持经过验证的本 fork NSIS 来源。官方 MSI、未知安装器、不同 Windows 用户范围、不同架构、跨安装目录搬迁先检测并明确说明边界；不能把这些来源当作已经受支持的 NSIS 覆盖升级。便携版保持既有手动更新路径。

## 4. 快照存储和单旧版规则

使用独立于可变业务数据目录的用户级回退根目录，例如已验证的本应用 LocalAppData 子目录。精确路径在实现时通过 Tauri/Windows 路径 API 解析，不拼接用户名，也不随 `app_paths.json` 切换而丢失。

```text
rollback/
  active.json                  # 唯一可回退点的 ID
  points/<point-id>/
    manifest.json
    cc-switch.db               # 保持来源 schema 的 SQLite 一致性备份
    files/                     # 受管文件内容，以内部 ID 存储
    inventory.json             # 路径、角色、哈希、权限、缺失状态
    package/                   # B 才持久保存来源 Setup、签名、固定清单
  transactions/<transaction-id>/
    journal.json               # 正在升级/回退/恢复的阶段
    staging/                   # 未发布的下一回退点
    rescue/                    # 本次操作失败时的程序与数据恢复材料
    helper/                    # 不在目标安装目录中的独立执行器
```

稳态只有一个 `points` 条目。事务期间允许旧回退点与候选点、当前状态应急副本短暂共存：它们用于失败恢复，不是可选的多个历史版本。

升级 `C → N` 的替换规则：

1. 当前 `C` 可有一个指向 `P` 的旧回退点。
2. 为 `C → N` 创建候选快照，失败时保留 `C → P`。
3. 安装及验证 `N`，未通过时不能删除原回退点。
4. 事务成功后发布唯一 `N → C` 指针，然后删除 `P` 和应急材料。
5. 若清理失败，新事务进入待清理状态，不展示 `P`，也不继续滚动生成第三代；提示重试清理。
6. 成功执行 `N → C` 后消费该回退点；`C` 不能继续回到 `P`。
7. 此后再次升级仍可建立新的 `N → C`，不会因一次回退永久禁用功能。

普通数据库备份属于既有功能，不作为版本回退历史链，也不为了“单旧版”删除用户自行保存的备份。禁止把 `points/` 和 `transactions/` 交给普通备份保留数量策略清理。

快照清单至少包含：格式版本、来源/目标完整应用版本、产品/fork 标识、安装来源、架构、安装目录、安装范围、用户身份、捕获时间、源 schema、实际数据目录、文件库存哈希、安装包绑定信息、事务 ID。应用版本不能从 schema 推算，也不能从仓库未被发布工作流改写的 `tauri.conf.json` 推算。

来源与目标包的版本、平台、SHA-256、签名、公钥 ID 和固定 Release URL 应绑定。SHA-256 用于本地完整性检查，minisign 用于签名验证；不能把普通哈希当成签名。未来新增的版本清单也需签名；历史包的版本绑定通过固定目标、验签以及安装后 PE/安装记录验证共同完成。

## 5. 捕获什么，如何保证一致

回退恢复的是 CC Switch 业务数据与其受管资源，不是整台电脑的系统还原。客户端自身新产生的会话和用户项目文件不在丢弃范围内。

| 对象                                   | 保存与恢复规则                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| CC Switch 数据库                       | SQLite Backup API 捕获已提交的 WAL 内容；备份后做完整性检查，记录原 `user_version`；恢复时不跑当前程序的迁移         |
| `settings.json`                        | 保存原始字节、权限与不存在状态，不用前端脱敏后的设置重建                                                             |
| `app_paths.json`                       | 只读解析真实 Tauri Store 路径；保存目录覆盖信息，确保恢复回同一来源数据目录                                          |
| 客户端配置、认证与模型目录             | 从代码中已存在的路径解析器列举具体文件，包含自定义目录；快照覆盖的文件按旧字节恢复                                   |
| MCP、提示词及引用文件                  | 数据库引用和实际文件要一一对应；记录路径与原始存在状态                                                               |
| CC Switch 管理的 Skill 内容与链接      | 不能仅恢复数据库的启用标记而留下新内容；盘点受管路径，保存必要内容及链接目标，避免递归复制整个仓库                   |
| 会话历史、用户项目、下载缓存、普通日志 | 不整体复制、不回滚、不删除；升级迁移若确实会改这些资源，必须有自己的恢复账本并接入事务，否则阻止声称完整可回退的更新 |
| 注册表、卸载项、快捷方式               | 由验证过的 NSIS 安装链管理；限定本应用身份，安装后核验，不导出或还原整个用户注册表                                   |
| 开机启动与代理状态                     | 恢复对应版本设置后按受控顺序重新应用；不让清理钩子在快照恢复后又覆盖数据                                             |

实现前输出一张完整的“代码写入点 → 文件解析器 → 快照/恢复策略”表。前面设计中笼统排除所有 Skills 内容不够严谨：若它与数据库引用相关，必须一并处理，不能显示旧状态却运行新文件。

一致性流程：

1. 网络下载和安装包预检在停机之前完成，避免长时间停代理。
2. 获取跨进程安装事务锁，暂停会话扫描、定时任务、WebDAV/S3 自动同步及新的配置写入。
3. 阻止并发切换供应商、修改设置、安装 Skill 和发起第二次更新；托盘、深链接等入口也受同一后端状态限制。
4. 停止接受新代理请求，排空正在进行的请求；超时则中止更新并恢复工作状态，不能静默截断。
5. 用可返回错误的退出清理撤回 Live 接管，保留可恢复的逻辑状态；等待后台任务和数据库连接全部退出。
6. 独立执行器在静止状态捕获数据库和文件；快照根目录仅允许当前用户及必要系统身份访问。
7. 检查文件在读取前后是否改变。外部编辑器仍在写入时重试，持续变化则中止捕获，不产出一半新一半旧的快照。

恢复前重新解析与核对目标路径，检查 reparse point、软链接、网络路径、越界以及实际用户身份。已经存在的受管链接必须按链接语义处理，不盲目跟随。

删除仅限清单证明“原先不存在、由本应用在事务后创建”的受管文件。不能递归删除整个 `.codex`、`.claude` 或自定义目录来实现“丢弃变更”。升级后新建受管文件需要写入所有权记录，否则不得凭目录位置删除。

第一版默认支持 Windows 本地磁盘。UNC/WSL、自定义身份和不支持的文件系统需要检测；未通过同等级恢复测试前，不把它们展示为可用回退点。

## 6. 安装器与独立执行器

建议增加一个小型 Rust 辅助程序，复用快照、验签和事务模块，但不启动 Tauri GUI、不初始化业务数据库。由 GA 构建，随签名 NSIS 包分发。相较复制整个当前 GUI exe，这样更容易证明它不会误触发迁移或后台任务。

手动 Setup 的正常升级顺序：

```text
识别旧安装和真实用户
→ 解出辅助程序到受限工作目录
→ 完成可恢复的程序/数据材料预检
→ 退出旧程序并完成捕获
→ 允许旧安装卸载/文件覆盖
→ 安装新版
→ 在正常初始化前验证事务
→ 新版完成数据库/设置/UI 启动握手
→ 发布新的唯一回退点
→ 清理上一代材料
```

第一阶段必须查明 CLI 2.11.5 生成模板的精确顺序。若现成 PREINSTALL 钩子晚于旧卸载，它就不是合格的捕获入口：改用受版本锁定的 NSIS 模板或更早的引导步骤。POSTINSTALL 可以验证结果，但不能作为唯一快照入口。

回退执行器顺序：

```text
两个确认均完成
→ 校验一次性执行票据与快照/包哈希
→ 获取事务锁并停止写入
→ 建立当前版本的临时应急程序/数据副本
→ 主程序退出，执行器确认进程结束
→ 安装目标旧版，明确禁止自动启动
→ 等待安装完成，核验退出码、目标 exe 和安装记录
→ 按持久化日志恢复旧数据及受管文件
→ 完成校验，启动旧版
→ 核验启动结果
→ 消费回退点并清理事务
```

执行要求：

- 用进程 API 传递参数并持有句柄，不拼接 shell 命令；中文、空格、特殊字符路径必须测试。
- 使用 NSIS 文档与实际包测试确认的无自动启动参数，不直接沿用 Tauri `/UPDATE` 语义。
- 验证安装目录仍是原目录，不能让旧版装进默认目录而留下两个实例。
- 新旧安装均不得在恢复完成前启动 GUI；兼容旧 `fork.3` 时不能依赖它理解新命令参数或事务格式。
- 新版支持启动握手；旧 `fork.3` 无握手能力，需在安装 E2E 中验证进程持续存活、窗口可用和数据读取，运行时状态文案不能伪称已获得应用级确认。
- 后台执行器默认隐藏窗口；安装器确实需要交互或 UAC 时如实呈现，用户取消必须进入可恢复状态。
- 处理任务栏快捷方式、单实例锁和残留进程；不能以进程名相同为由终止不属于目标路径的程序。

`portable.ini` 修复放在确认的 Setup 成功安装路径上。旧标记属于迁移资源，要记录原始状态；不在普通启动时自动删除，不修改真正 Portable ZIP 的行为。

## 7. 回退验证与两次确认

在“设置 → 关于”显示目标版本、快照时间、安装路径类别和 A/B 获取方式；只显示唯一目标，不给多版本列表。

点击“回退到上一版”后先进行只读预检：

- 回退点对应当前安装和当前版本，来源版本严格较旧。
- 数据库快照可读，schema 与来源元数据匹配，库存文件齐全。
- A 下载固定 Release 的签名包；B 重新验本地包的签名与版本绑定。
- 已有足够空间容纳暂存与应急材料，有写权限，无正在执行的更新。
- 来源是已测试的 Windows x64 NSIS 本 fork 安装。

验证成功进入第一层确认：

```text
回退到 vX？
恢复时间：YYYY-MM-DD HH:mm
供应商、设置、用量及受管配置将恢复到该时间。

[取消]                          [继续回退]
```

点击“继续回退”后先显示“校验回退目标…”并重新绑定预检结果；验证成功再打开独立的第二层警告。下载到缓存属于准备操作，两个确认前均不改正式数据库、配置和安装文件。

```text
最后确认：丢弃快照之后的变更
即将安装 vX，并恢复该回退点。
完成后不会保留更早版本的回退入口。

[确认回退并丢弃变更]            [取消]
```

交互细节：

- 两次按钮的视觉位置和 DOM 顺序都交换，不能只用 CSS 排序。
- 第二层打开时焦点落在“取消”；Esc、右上角关闭、遮罩关闭均只取消。
- 防止双击、Enter 连发和按住空格穿透第二层；弹层有独立实例和防重复提交状态，不用动画充当防抖。
- 第一层通过后，后端签发绑定目标版本、快照 ID/摘要、安装包摘要和短时有效期的一次性票据；第二层确认后才接受执行。
- 后端消费票据前再次验证状态，重复请求只执行一次；换包、换快照、过期或版本改变后要求重新预检与确认。
- 前端确认用于防误操作，不冒充对拥有本机用户权限者的安全隔离。
- 执行开始后显示当前阶段。对不可中断的替换阶段禁用取消，并给出真实结果，不能在子进程刚启动时显示“成功”。

## 8. 事务状态和失败恢复

候选状态如下，具体枚举名可在实现时调整：

```text
idle → preparing → prepared → quiescing → captured
     → installing → restoring（回退时）→ verifying → committed → cleanup

失败：failed → recovering → recovered
中断：检查 journal → 继续校验/补偿 → recovered 或需要处理
```

每一步先记录意图，落盘后执行，成功后再记完成；日志与指针替换使用经过 Windows 测试的耐崩溃写入方式。执行器重启后要能识别步骤已完成，不能重复删除文件、重复消费回退点或重复启动安装器。

| 故障位置                          | 要求                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------- |
| A 下载失败、B 缓存损坏、验签失败  | 不修改正式数据；保留回退点；B 可重新获取同一个目标包                         |
| 空间不足、文件变化、退出清理失败  | 不开始安装；释放事务锁并恢复暂停的服务                                       |
| 用户取消任一次确认                | 不安装、不恢复、不替换 active 指针                                           |
| 新版安装失败或首次启动失败        | 原回退点不被覆盖；使用事务应急材料恢复匹配的旧程序和旧数据                   |
| 旧版安装失败或部分安装            | 数据仍保持当前版本；修复当前程序、卸载记录和快捷方式，验证后才重新启动       |
| 已安装旧版但恢复数据失败          | 保持应用停止；恢复当前程序及当前数据的完整匹配集合，禁止旧 exe 读取新 schema |
| 任意文件恢复到一半断电/进程被终止 | 重启执行器根据日志幂等继续或补偿；不能凭文件存在判断整个恢复完成             |
| 旧版启动失败                      | 不消费回退点；保留事务材料与脱敏日志，进入恢复流程                           |
| 删除旧快照失败                    | 唯一可见回退点不变，提示清理失败，阻止产生额外历史代际                       |
| 云同步尝试恢复新版数据            | 事务中禁用同步；旧版首次启动保持自动同步暂停，提示用户重新选择同步方向       |

应急材料要包含当前版本可重新安装的已验签 Setup 或经验证的等价恢复集合，不能只有数据库。手动安装捕获的原安装文件和 B 缓存来源都要核验。应急包只为当前事务存在，不展示为第二个历史回退选项。

回退后暂停自动同步是一个明确的恢复保护状态；除此之外尽量还原快照中的设置。不能自动把恢复后的旧数据库上传覆盖云端，也不能自动下载云端的新 schema。

多文件回退期间可能被旧快捷方式手动启动是必须处理的测试项。第一阶段选择实际可证明有效的安装/进程启动阻挡机制；对于不理解事务锁的旧 `fork.3`，不能只靠新程序启动门禁。若 GA 演练不能保证隔离，不能发布为稳定可回退版本。

## 10. 按依赖实施的八个阶段

### P1：证明安装事务可行

工作：在 GA 用锁定 CLI 生成并归档 NSIS 脚本；核对钩子、旧卸载、降级、静默安装、自动启动、目录传递、用户范围和退出码；验证旧 `fork.3` 的实际安装行为。

产物：安装执行记录、准确参数契约、资源库存初稿、helper 形式选型、旧版启动阻挡方案。

通过条件：能在原文件首次被改前捕获；能安装旧版而不启动它；能取得真实安装结果；能恢复当前安装。这是后续编码的前置证据，不凭文档猜参数。

### P2：实现单回退点与快照核心

工作：清单校验、指定位置的 SQLite Backup、文件存在/缺失和 ACL/链接库存、哈希、受限访问目录、空间预检、候选点发布、事务日志和清理。

通过条件：WAL 数据完整；捕获不改变来源 schema；故障后旧 active 不丢；滚动升级始终只有一个可用旧版本。

### P3：实现 A/B 包获取与验证

工作：固定 fork Release 查包；精确版本与架构匹配；B 升级前缓存来源包；离线二次验签；B 损坏后转 A；准备安装失败恢复用当前包；支持下载取消。

通过条件：篡改、错误公钥、错误版本/平台/来源、HTML 错误响应均被拒绝；B 断网可完成预检；普通自动更新仍只接受更新版本。

### P4：接入升级与首版手动覆盖

工作：事务停机、暂停同步、NSIS 预覆盖捕获、旧版来源识别、首次启动门禁、健康验证与单旧点滚动发布；处理遗留 `portable.ini`。

通过条件：旧 `fork.3` 手动安装首版后真实得到 A 回退点；带协议的旧版升级得到 B 回退点；重装同版本不覆盖；新安装无虚构回退点。

### P5：实现回退执行与补偿

工作：执行器、等待主进程退出、无自动启动安装、程序验证、旧数据恢复、不存在项处理、旧版启动、回退点消费、断电和失败恢复。

通过条件：任一步失败都不启动不匹配的程序/数据库组合；恢复操作可重试；失败时应急材料完整；成功后不暴露更早历史链。

### P6：实现用户入口与双重确认

工作：About 回退卡、预检、目标信息、两次位置相反的按钮、默认取消焦点、一次性票据、阶段显示、失败重试与无动画交互。

通过条件：取消、连击、按键重复、过期票据、重复 IPC、切页再回均不误执行。界面不把准备成功当回退成功。

### P7：执行整套 GA 验收

工作：运行现有前后端 CI、新单元/集成测试、真实 NSIS E2E 和故障注入；归档安装包、哈希、生成脚本及脱敏状态记录。

通过条件：下节核心场景全过，且旧功能 CI 无回归。安装测试必须使用构建产物，不用仅模拟“安装成功”的单元测试替代。

### P8：制作一个完整稳定候选版本

工作：生成候选签名 Setup，复核 fork 公钥与 endpoint，确认回退固定资产存在；对同一提交完成 Windows 验收，再由既有发布流程发布稳定版本。

通过条件：`fork.3 → 候选版 → fork.3` 真实可用；B 路线用临时测试版本已证明；Release 签名、版本清单和 `latest.json` 一致。未通过则继续修复候选，不把半成品推为 latest。

P2 与 P3 都依赖 P1；P4 依赖 P2/P3；P5 依赖 P4；P6 可在接口确定后实现，但交付依赖 P5；P7/P8 必须基于完整实现。每阶段形成可审查提交，不等于必须逐阶段发布给用户。

## 11. GitHub Actions 测试矩阵

测试版本至少准备 `T1 / T2 / T3 / T4`，仅用于隔离的测试产物，不创建四个公开稳定 Release。使用合成数据库、假凭据和固定客户端配置；所有测试 home、安装目录、注册表范围和 Tauri Store 都隔离，不能只设置一个可能被库忽略的 HOME。

| 场景                                     | 必须验证的结果                                                     |
| ---------------------------------------- | ------------------------------------------------------------------ |
| 旧生产 `fork.3 → T1 → fork.3`            | 手动安装生成 A；旧包签名有效；恢复旧数据库和配置；不依赖旧版新协议 |
| 无协议旧版应用内更新至 T1                | 安装钩子补捕获成功，来源标为兼容 A，不假称 B                       |
| `T1 → T2` 应用内升级，随后断网回退       | B 离线验签和安装完成                                               |
| `T1 → T2 → T3 → T4`                      | T4 只保存 T3；回到 T3 后没有 T2 入口                               |
| `T1 → T4`                                | 回到真实来源 T1，不下载从未安装过的 T3                             |
| 重装同版本                               | 原回退点不被覆盖                                                   |
| 全新安装、Portable、未知来源             | 无误报的可执行回退入口                                             |
| B 缓存被删/篡改                          | 不执行损坏包；只对同一目标走 A 重新验证                            |
| A 404、超时、签名错误                    | 不触碰正式数据，不消费快照                                         |
| 合成 schema 19 → 20 → 19                 | 回退不经过新程序迁移，不需要合入 4.0 预览代码                      |
| 数据库 WAL 存在、普通备份清理            | 已提交数据不丢，版本快照不被普通备份轮换删除                       |
| 自定义目录、空格/中文路径、另一盘符      | 来源解析、目标安装、权限及跨卷恢复正确                             |
| 设置、MCP、提示词、受管 Skills 变更      | 数据库引用与磁盘内容匹配，非受管文件不受影响                       |
| 原文件不存在、升级后创建受管文件         | 只删除库存/账本授权的新增文件                                      |
| 双击、Enter/空格连发、Esc、重复 IPC      | 两次确认不能被穿透，执行至多一次，按钮顺序确实相反                 |
| 快照捕获/安装/恢复每个阶段强制中止       | 日志可恢复，回退点不丢，不启动混合版本状态                         |
| 空间不足、权限不足、文件被占用、清理失败 | 提供可重试结果，不静默跳过必要文件                                 |
| 外部配置并发写入、代理长请求、云同步     | 正确等待或中止，恢复期间没有旁路写入                               |
| 重启/重新登录/旧快捷方式在事务中启动     | 程序不得抢跑读取过渡数据；断电恢复路径可执行                       |
| NSIS 用户取消、降级拒绝、错误目录        | 检测真实失败，修复当前程序与数据，不错误报告成功                   |
| Setup 覆盖含 `portable.ini` 的目录       | 成功安装后按安装版识别；Portable 包仍按便携版识别                  |

GA 分工建议：

- 保留现有 Frontend Checks 和 Windows/macOS/Linux 后端检查，跨平台编译用于证明条件编译没有回归，功能安装验收仅 Windows。
- 新增可手动触发的 Windows rollback E2E 工作流；推特性分支后通过 PR 或 workflow_dispatch 运行，避免现有 CI 仅监听 main 导致无人测试。
- 纯状态机/快照测试、前端交互测试先跑；实际旧 Setup 与候选 Setup 安装往返随后跑。
- 使用测试专用签名密钥验证故障，生产签名 Secrets 仅在可信发布任务使用，不暴露给任意 PR。
- 一次重启恢复演练需要可控的临时 Windows runner/VM；如果 hosted runner 无法恢复同一磁盘状态，增加隔离 VM 或人工执行 GA 产物的记录，不能把进程 kill 等同于整机重启通过。
- 不在真实用户电脑上编译或直接执行试验性回退。计划和实现阶段均不删除用户数据。

## 12. 稳定发布标准与最终交付

稳定候选必须同时满足：

- A、B 均完整可用，且首个版本能从已发布旧版升级后回退。
- 一个上一版快照滚动替换，任意升级次数和跳版本都正确，失败不抢先删除旧回退点。
- 回退按钮两次确认、位置对调、防连击和后端一次性执行均通过测试。
- 包签名、快照一致性、实际安装、旧数据恢复、失败补偿、重启恢复均有证据。
- 用户真正拿到的签名包与验证提交一致；恢复所需固定 Release 资产完整保留。
- 关于页说明回退目标和恢复时间，明确丢弃范围与云同步暂停；不宣称“整台电脑所有变更都会恢复”。
- 稳态没有多代版本包、应急目录或失效回退点堆积；未成功清理时有可见状态。

交付包括实现代码、安装钩子/模板、执行器、测试与 GA 工作流、对应运行记录、完整稳定候选安装包及发布说明。首版不承诺跨平台、跨 MSI/NSIS、任意历史版本选择、无快照降级或自动保留升级后的数据。

本轮只交付这份计划。后续实现时按以上门禁逐步推进；不把 4.0 预览迁移作为回退功能的前置条件，也不为本轮计划触发构建或发布。
